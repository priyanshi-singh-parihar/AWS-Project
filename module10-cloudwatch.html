Module 10: Amazon CloudWatch

⏱️ Est. Time: 45 Mins ⚙️ Services: CloudWatch, SNS, EC2 💰 Cost: Free Tier Eligible

Core Concept & Real-World Utility

CloudWatch is the centralized observability hub for AWS. It aggregates metrics, logs, and events across your infrastructure. In production, proactive monitoring is non-negotiable; you must configure automated alarms to detect memory leaks, disk space exhaustion, or CPU spikes before they cascade into system outages.

Architecture Integration

CloudWatch monitors the vital signs of our entire architecture. It tracks ALB request counts, EC2 CPU utilization (feeding data to our Auto Scaling Group), and RDS connection limits. We also stream application error logs directly to CloudWatch Logs so we can debug Python exceptions without SSHing into multiple servers.

⚖️ Architecture Trade-off Analysis

CloudWatch Observability vs. Data Ingestion Costs: Centralized metrics and log streaming provide instant visibility and proactive alerting. However, storing large volumes of custom log streams and high-resolution metrics past the free tier allowance incurs recurring ingestion and storage fees.

To verify that our CloudWatch Alarms and Auto Scaling tracking policies work, we install a stress-testing utility via the terminal to artificially peg the CPU at 100%.

# Step 2: Launch a CPU stress test utilizing 100% of all CPU cores for 10 minutes

Debugging & Troubleshooting

Error: Custom Memory/RAM metrics are not appearing in CloudWatch.
If you installed the CloudWatch Agent but no data is appearing, it is an IAM permissions issue. The EC2 instance must have an IAM Role attached that includes the CloudWatchAgentServerPolicy. Without this policy, the agent runs locally but its API calls to push data to AWS are denied.
